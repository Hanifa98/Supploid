# Supploid.com

A complete static Astro 5 website for aviation-led wholesale sourcing, with an industrial supply path and separate premium AOG support. Citron is the working accent. The public quote wording is “Fast quoting, documentation supplied”. Premium AOG remains a separate service available 24/7.

Public registration numbers, street addresses, maps, and phone numbers are deliberately omitted at the user’s request. The site uses `info@supploid.com` and `aog@supploid.com`. Customer callback numbers are still requested in the forms.

## Included

- Homepage, about, sourcing approach, six capability detail pages, capability index, contact, full RFQ, premium AOG, four procurement articles and their index, privacy draft, terms draft, and 404 page.
- Static HTML generated by Astro. No frontend framework, CMS, content database, animation library, or third-party font request.
- Repository-owned markdown content, self-hosted Inter Variable (Latin and Latin Extended), AVIF/WebP engineering illustrations, native scrolling and CSS motion, reduced-motion support, responsive navigation, and accessible forms.
- Single-inquiry quote form on the homepage and quote page. Aviation requires a part number; Industrial starts with a required description and makes the part number optional. Quantity, first name, last name, email, and message are required. Phone and company name are optional. Values survive category switching.
- Light/dark themes follow the visitor’s system preference until an explicit choice is stored. The preference is applied before first paint; theme changes do not change spacing or type scale.
- Cloudflare Pages Functions for `/api/quote` and `/api/aog`, server-side Turnstile verification, hostname/action checks, input validation, Resend internal notification and customer confirmation, HTML/text bodies, and retry-safe provider idempotency keys.
- A small auxiliary Durable Object Worker enforces five unique requests per hashed IP in a rolling hour, shared across both endpoints. It stores timestamps and request fingerprints only, not form contents. Retries of an identical request reuse quota. This is abuse-protection state, not a website content or customer database.
- Per-page social images, canonical URLs, structured data, sitemap, and robots configuration.

## Run locally

Use Node.js 22.12 or newer and npm. The package lock records the installed dependencies.

```sh
npm ci
npm run dev
```

Astro prints the local URL, normally `http://127.0.0.1:4321`. For a static preview:

```sh
npm run build
npm run preview
```

The asset prebuild generates AVIF/WebP files from the source engineering illustrations. The postbuild generates social-card PNGs, `sitemap.xml`, and `robots.txt`. The build output is `dist/`.

The supplied archive already includes a built `dist/`. To review it without installing Node dependencies, run `python3 -m http.server 4321 --bind 127.0.0.1 --directory dist` from this folder, then open `http://127.0.0.1:4321`. This serves the static preview and email-draft forms; it does not run the delivery endpoints.

If your local environment restricts Astro’s telemetry preferences directory, set `ASTRO_TELEMETRY_DISABLED=1`. On the machine used for this build, native compiler reads under Documents stalled; the same project was verified in an isolated `/private/tmp` build directory. The deliverable source and built output remain in this folder.

## Default preview behaviour

Live form delivery is disabled by default. Both forms validate input and prepare an email draft plus a downloadable text request. Long inquiries can be downloaded and attached manually to the email draft. The web forms do not accept file uploads. No request is sent merely by pressing “Prepare email request”.

Server endpoints return a clear unavailable response until live delivery is configured. Preview builds are `noindex` and disallowed by `robots.txt`. No analytics script is loaded without its public token.

Privacy and sale terms are visibly marked drafts. The retention period, controller wording, adopted commercial policies, premium-service terms require owner review. No public company identifiers or phone numbers have been added to satisfy those open items automatically.

## Cloudflare Pages

For the full ordered deployment procedure, including GitHub, the Durable Object Worker, Pages settings, secrets, domain setup, and production checks, see [DEPLOY-CLOUDFLARE.md](DEPLOY-CLOUDFLARE.md).

1. Put the project source in the repository Cloudflare will build. Do not upload `node_modules` or secrets.
2. Create a Pages project. Set the root to this project directory, build command to `npm run build`, output directory to `dist`, and Node version to a supported Node 22 release.
3. Deploy the auxiliary limiter Worker first from `workers/rate-limiter/` using its Wrangler configuration. Its Durable Object binding is then referenced by the Pages `wrangler.jsonc`.
4. Configure the environment values below in Cloudflare. Preview and production values are separate. Add the intended hostnames to both Turnstile and `ALLOWED_HOSTNAMES`; preview form delivery remains off unless explicitly configured.
5. Bind the custom domain only when the content and delivery flow are ready for launch. The site’s canonical base is `https://supploid.com`.

The following commands deploy resources; they are documented, not executed as part of this local build:

```sh
npx wrangler deploy --config workers/rate-limiter/wrangler.jsonc
npx wrangler pages deploy dist --project-name supploid
```

For Pages Functions local development, run the limiter Worker locally in a separate terminal, then `npm run pages:dev`. Wrangler can connect the external Durable Object using the matching script name. Copy `.dev.vars.example` to `.dev.vars` and configure only test credentials for development. The plain Astro dev server does not execute Pages Functions.

The static site does not require an Astro Cloudflare SSR adapter. Pages Functions are deployed from the root `functions/` directory. `_routes.json` limits Function invocation to `/api/*`.

## Configuration

| Variable / binding | Location | Purpose |
| --- | --- | --- |
| `PUBLIC_TURNSTILE_SITE_KEY` | Build-time public value | Turnstile widget key; may appear in HTML |
| `PUBLIC_FORMS_ENABLED` | Build-time public value | `true` only after final privacy/retention review and delivery configuration |
| `PUBLIC_INDEXABLE` | Build-time public value | `true` for the indexable launch build; default preview remains noindex |
| `PUBLIC_ANALYTICS_TOKEN` | Build-time public value, optional | Cloudflare Web Analytics; leave empty to omit tracking |
| `RESEND_API_KEY` | Cloudflare secret | Sending-domain authorised Resend key; server only |
| `TURNSTILE_SECRET_KEY` | Cloudflare secret | Siteverify secret; server only |
| `REFERENCE_SECRET` | Cloudflare secret | At least 32 random characters for HMAC request IDs and hashed IP identifiers |
| `NOTIFY_EMAIL` | Cloudflare server variable | Defaults to `info@supploid.com`; all web submissions arrive here |
| `ALLOWED_HOSTNAMES` | Cloudflare server variable | Comma-separated exact allowed hosts; default `supploid.com,www.supploid.com` |
| `FORMS_ENABLED` | Cloudflare server variable | Must be `true` for online delivery |
| `RFQ_LIMITER` | Durable Object binding | Class `RfqLimiter` in Worker `supploid-rate-limiter` |

Never prefix a server secret with `PUBLIC_` or place it in source. `.env` and `.dev.vars` are ignored. Client scripts never reference the Resend or Turnstile secret keys.

After configuring the deployment, use `npm run launch:check` in a properly configured environment to identify remaining content/configuration items. This check deliberately fails while policies are drafts. It does not create credentials or contact an account.

## Email and DNS setup

Verify `supploid.com` as a sending domain in Resend. Copy the exact DNS hostnames, types, priorities, and values from the Resend dashboard; account- and region-dependent record values are not guessed in this project.

- Add the Resend-provided **DKIM TXT** record at its specified selector.
- Add the provider-specified **SPF TXT** and **MX** records for the return-path subdomain, commonly `send`. These are sending records, not replacements for your main inbound mailbox MX records.
- Ensure the domain’s SPF policy is valid. Do not create multiple SPF TXT policies at the same hostname; merge authorised senders when applicable.
- Publish a **DMARC TXT** policy at `_dmarc.supploid.com` appropriate to the domain’s real mail configuration and reporting arrangements. Do not invent a reporting mailbox that is not monitored.
- Keep existing receiving-mail records intact. Confirm `info@supploid.com` and `aog@supploid.com` are monitored mailboxes or forwarding addresses. A verified sending domain does not create receiving mailboxes.

Internal messages use `Supploid RFQ <rfq@supploid.com>`, with the requester as Reply-To. Customer confirmations use `Supploid <noreply@supploid.com>`, with `info@supploid.com` or `aog@supploid.com` as Reply-To. The default internal recipient for both forms is `info@supploid.com`; the premium AOG subject is prefixed `[AOG]`.

References: [Resend domain setup](https://resend.com/docs/dashboard/domains/introduction), [Resend email API](https://resend.com/docs/api-reference/emails/send-email), [Turnstile server validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [Pages bindings](https://developers.cloudflare.com/pages/functions/bindings/).

## Reliability and data handling

The endpoint checks configuration and request origin, bounds request size, verifies Turnstile, checks the honeypot, validates the inquiry data, applies the shared rolling limit, and sends the internal email before the customer confirmation. A success is returned only after both provider requests are acknowledged.

An internal-send failure returns an error with the email fallback. If the internal message succeeds but the customer confirmation fails, the response explicitly states that the request was received and includes its reference. A provider acknowledgement is not proof of final mailbox delivery; deployment testing must check the actual inbox and Resend events.

Identical validated requests use stable Resend idempotency keys. The five-character reference is derived from a keyed digest of the random submission ID and contents; it is not an access token. No quoting system, stock database, or document certification service is implied.

The limiter uses strongly consistent per-key state rather than eventually consistent KV counters. Its alarm removes expired state. Native Workers rate-limit bindings use short windows, so this project uses a Durable Object for the requested rolling hour. Cloudflare resource availability and billing depend on the selected account plan.
